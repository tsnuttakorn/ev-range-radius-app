# Changelog

All notable changes to the **ev-range-radius-app** will be documented in this file.

## [1.0.0] - 2026-08-15

### Added
- **Custom Slider Component**: Replaced `@react-native-community/slider` with a hand-built `CustomSlider` (`src/components/CustomSlider.tsx`) for the three range-panel sliders (Battery SoC, Reserve Buffer, Charge Limit), giving full control over its visuals: a hairline track with a soft two-layer glow instead of a chunky filled bar, five faint precision tick marks, and a miniature battery-gauge thumb whose own fill level tracks the value live as you drag — fitting for an EV app, since the handle you drag doubles as the read-out.
- **Driving Mode (City / Mixed / Highway)**: New setting feeding directly into the range formula, alongside the existing rating standard and AC toggle. City driving applies a +10% range factor (regenerative braking / low speeds beat the official rating), Highway applies −20% (aerodynamic drag costs more at sustained speed), Mixed is the neutral baseline the rating standards already approximate. Also drives the reference speed used for the drive-time estimate (40 / 90 / 110 km/h respectively) — independent of the range factor, since a slower city speed doesn't imply less range, just that covering it takes longer. Selectable via a new 3-segment picker in `RangeControlPanel`, persisted in `useEVStore` (default Mixed). Also wired into `TripPlannerService`'s trip-leg math (see Fixed below), so a full trip plan — not just the main panel's standalone figure — reflects the selected mode.
- **Formula Documentation**: New `docs/range-calculation-formula.md` documenting every constant and formula behind the app's range/energy/time figures — rating standard factors, AC penalty, driving mode factors (individually and combined per standard × mode × AC on/off), and the full downstream formula table (Safe Range, Max Range, Max Buffer Range, Usable Energy, Efficiency, drive/charge time), plus a worked numeric example.
- **New App Icon (Map Pin + Bolt)**: Replaced the charging-port glyph with a location pin with a lightning bolt cut clean through it — reads more directly as "find a charger near you" and holds up better at small sizes than the previous port-shaped glyph. Same brand gradient (teal `#2dd4bf` → sky `#38bdf8`) and dark-navy range-ring background as before for continuity. Regenerated the full referenced set — `icon.png`, `icon-light.png`, `adaptive-icon.png`/`adaptive-icon-background.png`/`android-icon-monochrome.png`, `splash-icon.png`, and a simplified flat `favicon.png` (gradients don't read at 16–48px, so it's a solid teal square with a white bolt instead). Previous set backed up to `assets/.icon-backup-2026-08-15/`. The static export in `assets/app-icons/AppIconPack/` (per-platform slices for bare-workflow use, plus the shareable `EV-App-Icon-Pack.zip`) was also regenerated in full from the same source — `expo-assets/`, `ios/AppIcon.appiconset/*` (all 18 sizes Contents.json lists), `android/mipmap-*/` (5 densities × 5 files), `android/playstore-icon-512.png`, `web/*` (touch icon + favicons), and `source/*` (masters + a hand-authored `icon-master.svg` matching the new pin+bolt geometry). `README.md` updated to describe the new design.
- **New Icon Not Showing Up on Android Device Builds**: Updating `assets/icon.png` etc. alone has no effect once a project has a committed native `android/` folder (this one does, from a prior `expo prebuild`) — the launcher actually reads already-baked PNGs under `android/app/src/main/res/mipmap-*/ic_launcher*.png`, generated once and never touched by Metro/Fast Refresh. The usual fix, `expo prebuild --clean`, wasn't safe to run here: this `android/` folder also carries hand-written native Android Auto code (`EVCarAppService.kt`, `EVMapScreen.kt`, `EVSearchScreen.kt`, manually-edited `AndroidManifest.xml`/`build.gradle`) that isn't wired through an Expo config plugin, so a full prebuild would've silently deleted it. Regenerated just the 25 baked launcher icon PNGs (5 files × 5 densities) directly from the new source assets in place instead, leaving the manifest, gradle files, and Android Auto Kotlin sources untouched.

### Added
- **Location Permission Gate on App Start**: New `LocationPermissionGate` (`src/screens/LocationPermissionGate.tsx`), wrapping `HomeScreen` in `App.tsx`. Previously, location permission was only ever requested silently deep inside `EVMapAdapter` — a user who denied it (intentionally or by reflex) got no explanation and no way back in short of finding the OS Settings screen themselves, while the map, range circles, and trip planner all silently degraded around a placeholder location. The gate now gets a screen of its own before the app renders: checks the current permission status on launch and skips straight through if it's already `granted` (so returning users never see it); if undetermined, shows a branded explanation with an "Enable Location" button; if denied, blocks with an "Open Settings" button and re-checks automatically via an `AppState` listener when the app regains focus (the OS won't re-show its own prompt once denied, so Settings is the only way back). Existing `requestForegroundPermissionsAsync()` calls inside `EVMapAdapter` are unaffected — calling it again after a decision has already been made is a no-op that just returns the cached status, so nothing double-prompts.

### Fixed
- **Native Android Splash Screen Still Showing an Unbranded Placeholder**: Auditing every remaining reference to the app icon after the pin+bolt redesign turned up `android/app/src/main/res/drawable/ic_launcher_background.xml` — a separate `@drawable/ic_launcher_background` resource (distinct from the `@mipmap/ic_launcher_background` PNG the adaptive icon uses, despite the shared name) that `styles.xml`'s `Theme.App.SplashScreen` sets as the activity's `windowBackground`, i.e. the actual native splash screen shown instantly on cold launch before JS loads. It layers `colors.xml`'s `splashscreen_background` (`#FFFFFF`) under `drawable-*/splashscreen_logo.png` — a generic gray placeholder graphic, not the app's branding at all (old or new), on a plain white background, contradicting `app.json`'s configured dark `#0B0F16` splash. Neither of the two icon-update commits above touched this, since neither `assets/icon*.png` nor `AppIconPack` feed it. Regenerated `splashscreen_logo.png` at all 5 densities from `assets/splash-icon.png` and changed `splashscreen_background` to `#0B0F16` to match `app.json`.
- **Long Trips Failed to Plan on a Fresh Install (No Station Coverage Past the First Waypoint)**: Despite the "corridor routing" name of an earlier perf pass, station data was actually a single fetch centered on the vehicle's *current position* (`COUNTRY_SEARCH_RADIUS_KM`/`COUNTRY_MAX_RESULTS` in `EVMapAdapter.tsx`), then just filtered locally per hop by `TripPlannerService`. On first launch this had no upstream mitigation: with the offline cache empty and (typically, on a fresh checkout) no `EXPO_PUBLIC_OCM_API_KEY`/Google key set, `getAllRealStations` fell back to `generateMockStations`, which only produced 8 fixed stations within the *vehicle's own range* of the origin — nowhere near enough for a ~1000km trip. Even with real API keys configured, `mergeStationSources`'s closest-500 distance-sort truncation and Overpass's 800km radius cap meant real coverage could still thin out or vanish for the back half of a long route. Added `getCorridorStations` (`src/utils/StationService.ts`) and `samplePointsAlongRoute` (`src/utils/StationGenerator.ts`): the trip-planning effect now fetches the actual driving route up front and fans OCM + OSM/Overpass queries out to waypoints spaced ~150km along it (capped at 12 samples, each with its own independent result budget), seeding deterministic per-waypoint mock stations only where a waypoint has zero real data. Station coverage for a long trip is no longer bounded by how close a spot happens to be to wherever the vehicle currently sits.
- **Slider Touches Swallowed by the Map (Android)**: The range-panel sliders sit as an overlay on top of `react-native-maps`' `MapView`, which on Android renders through a native `SurfaceView` that intercepts touches ahead of JS-rendered siblings regardless of visual z-order/`zIndex` — so touches meant for the sliders were being consumed by the map underneath instead. Fixed by forcing the panel onto its own Android hardware layer (`renderToHardwareTextureAndroid`), which restores correct touch routing.
- **Slider Drag Silently No-Op'd**: `CustomSlider`'s `PanResponder` was built via `useRef(PanResponder.create(...))`, whose callbacks captured the track's `width` from the very first render — permanently `0`, since layout hadn't measured yet at that point. Tapping still visually "worked" (the press-scale animation ran regardless), but every drag move was silently dropped since the stale `width` always failed its `> 0` check. Fixed by reading width through a ref instead of the stale closure.
- **Touching the Slider Thumb Itself Reset the Value to 0**: `locationX` on a touch event is relative to whichever sub-view the finger actually lands on, not the `PanResponder`'s own view — so tapping directly on the visible thumb (battery icon) computed a position relative to that ~19px icon instead of the full track, snapping the value to ~0%. Fixed by making the thumb visual `pointerEvents="none"` so every touch, including ones landing on the thumb, is always measured against the track's actual width.
- **Backup/Alternative Charging Station Could Require Backtracking, and Wasn't Necessarily the Nearest**: The backup route's first stop was scored the same way as the primary pick — closest to the *destination* — which could pick a station far from the driver's actual position, or one behind them relative to the destination. The backup pick is now scored differently: stations that would require backtracking (not actually closer to the destination than the current position already is) are excluded outright, and among what's left, the physically nearest reachable station wins.
- **`persist` Middleware Hit AsyncStorage on Every Slider Tick**: Zustand's `persist` subscriber fires on every `set()` call to the store, not just ones touching a persisted field — so dragging any slider (including Battery SoC, which isn't even persisted) was re-serializing the persisted state slice and hitting the AsyncStorage native bridge dozens of times a second, a likely contributor to drag stutter. Fixed by debouncing the storage adapter's writes (500ms) rather than throttling the app state updates themselves, so drags stay fully in-memory/fast and only the settled value gets written to disk.
- **`RangeControlPanel` Content Inset Further Than the Card Above It**: The sliders/toggle section had its own `paddingHorizontal: 4` that the summary card above it didn't, so slider content sat 4px further in than the vehicle pill and SAFE RANGE figure directly above. Removed — both sections now align to the same edges via the panel's own outer padding.
- **Slider Thumb Too Close to the Card Edge**: With that alignment fix, the battery-gauge thumb's icon (which extends a few px past the 0%/100% track ends by design) now had no clearance from the card border at the extremes. Wrapped each `<Slider>` in a small horizontally-padded `View` — kept outside `CustomSlider` itself rather than as internal padding, since its `PanResponder` measures touch position as `locationX / its own layout width`; padding internally would've left the visual track narrower than that divisor and thrown off tap/drag accuracy at the edges.
- **Overpass (OSM) Station Requests Missing a `User-Agent`**: `getOverpassStations` was sending requests to the public Overpass API without a `User-Agent` header, which the service can reject or rate-limit more aggressively for unidentified clients — a plausible contributor to the `[Overpass] Failed to fetch OSM charging stations: AbortError` warnings seen in testing. Added an explicit `User-Agent` identifying the app.
- **Trip Plan Didn't Recalculate on Driving Mode (or Other Range-Panel) Changes**: `TripPlannerService.planSmartTrip` had no `drivingMode` input at all — trip-leg reachability and drive-time math always assumed Mixed regardless of the driver's selection. Added `drivingMode` to `PlanSmartTripInput`, threaded it through the per-leg range/reachability calculation and the drive-time estimate, and added it to `EVMapAdapter`'s trip-planning effect dependencies so a mode change re-plans the whole trip, not just the main panel's standalone range figure.
- **Map's Range Circles Silently Stopped Updating on Slider/AC/Driving-Mode Changes**: A side effect of the earlier store-subscription fix (see "Unfiltered Store Subscriptions" below) — `HomeScreen`'s new `useShallow` selector only included `userLocation`/`activeVehicle`/`themeMode`, but `getCalculationResult()` (which drives the map's `safeRadiusKm`/`maxRadiusKm` circles) also depends on `currentSoC`, `targetReserveSoC`, `preferredMaxChargeSoC`, `isAirConActive`, and `drivingMode`. Since `getCalculationResult` is a stable function reference, changing those fields no longer re-rendered `HomeScreen` at all, so the map's circles went stale on every slider drag or AC toggle — not just driving mode. Added the missing fields to the selector.

### Changed
- **Unfiltered Store Subscriptions Caused Unrelated Re-renders**: `RangeControlPanel`, `EVMapAdapter`, `HomeScreen`, `LocationSearchField`, and `VehicleSelectModal` each called `useEVStore()` with no selector, subscribing to the *entire* store — so dragging a slider was also re-rendering the full map (`MapView` + markers/polygons), the search field, and other unrelated UI on every tick, and vice versa. Switched all five to `useShallow`-scoped selectors picking only the fields each component actually reads.
- **`CustomSlider` Render Cost While Dragging**: `PanResponder.create(...)` was being re-invoked (and its result discarded) on every render; now built exactly once via `useState`'s lazy initializer, reading live min/max/step/callback through a ref so it never needs rebuilding mid-gesture. Wrapped the component in `React.memo` so dragging one slider no longer re-renders the other two in the same panel. Memoized the derived halo/tick colors instead of re-parsing the same hex strings every drag frame.
- **Range Formula Standards Loosened**: NEDC raised from 0.72 → 0.90 (in several steps, in response to real-world range consistently coming in above the app's estimate — not calibrated against a specific vehicle's logged numbers, so may need further tuning against real before/after figures). WLTP and EPA both raised to 1.00 — the vehicle's rated range is now treated as its achievable ceiling for those two standards rather than discounted further by default. AC penalty loosened from 0.93 → 0.95.

## [1.0.0] - 2026-08-14

### Added
- **Automatic Real-Time Location Tracking**: The car pin now follows the device's live GPS position continuously from app start (via `Location.watchPositionAsync`), instead of only updating on an explicit recenter/drag/search action. Automatically pauses itself if the position is manually overridden (dragging the pin, or picking a custom "FROM" start point), so it doesn't fight that override mid-trip; the "Current" chip in the FROM row resumes it. The top-right location button is a plain "snap the camera back to the pin and zoom in" action — it no longer toggles tracking or re-fetches GPS itself (that was slower and could fail/hang); it just pans to the already-tracked position.
- **Correct Location on First App Open**: The map previously opened centered on a hardcoded fallback coordinate (not the device's actual location) until the user manually tapped the location button. `EVMapAdapter` now silently requests location permission and fetches the real GPS position once on mount, updating the pin and camera automatically; falls back to the default location only if permission is denied or GPS fails.
- **Car Emoji Pin for Current Location**: Replaced the platform's default red map pin at the current/selected location with a themed circular badge containing a car emoji (🚗) — background color follows the light/dark theme (`t.surface`), with a brand-teal border. Re-snapshots correctly on theme toggle (previously the native marker bitmap wouldn't refresh until something else, like dragging the pin, forced it).

### Fixed
- **"Max Buffer Range" Ignored the Reserve Buffer Slider**: The sub-metric previously showed the same value as the map's outer-boundary "Max Range" (0% SoC, i.e. driving to completely flat) — a figure that's deliberately independent of the reserve buffer by design, so adjusting the reserve slider had no visible effect on it at all. Added a new `maxBufferRangeKm` calculation — best-case range at a full charge while still respecting the reserve buffer, i.e. `(100% - reserve%) × total range` — and switched the panel to display that instead. The map's outer polygon still uses the original 0%-SoC `maxRangeKm`, unchanged.

## [1.0.0] - 2026-08-13

### Changed
- **DC Charging Strictly Preferred Over AC**: The trip planner now treats DC as a hard preference at every hop — including for the backup/alternative route — instead of a soft scoring penalty. If any DC charger is reachable, AC options are dropped from consideration entirely; a farther DC charger always wins over a closer AC one. AC is only ever picked when no DC charger is reachable within safe range at all.

### Fixed
- **Uneven Max DC/AC Charge Input Row in Garage's Custom Vehicle Form**: The "Max DC Fast Charge (kW)" placeholder (`"e.g., 130 (CCS Combo / CCS2)"`) was much longer than the "Max AC Charge (kW)" placeholder (`"e.g., 6.6"`) despite both inputs sharing an equal-width half row, causing it to overflow/clip and look uneven against its neighbor. Shortened to `"e.g., 130"` to match.
- **Directions Button Text Overflow on Backup Stop**: The "Directions from {suggested stop name}" button label could overflow/wrap awkwardly when the suggested stop's name was long. Shortened to a fixed "Directions from Suggested Stop" label, with `numberOfLines`/ellipsis as a safety net regardless of name length.
- **Backup Stop Directions Started From GPS Instead of the Suggested Stop**: The "Get Directions in Google Maps" button on a backup/alternative charging stop's detail card omitted an origin, so Google Maps defaulted to the device's current GPS location — not useful for comparing "how far is this backup stop from the stop I'm actually planning to use." It now detects when the card is showing a backup stop and sets the primary/suggested stop as the directions origin instead, with the button label changing to "Directions from {suggested stop name}" to make that explicit.

### Added
- **Compare Backup Charging Station on Map**: The backup/alternative route card in the trip itinerary now has a "View on map to compare" toggle. Tapping it pans the map to the backup station's location and opens its detail card, so it can be visually compared against the primary pick; tapping it again ("Back to trip") deselects it and pans back to the origin. The backup stop now also gets its own hollow "B" badge marker on the map (previously it blended in as a plain, unlabeled pin), and its route line switches from a muted dashed line to a solid brand-colored one while actively being compared, so both the suggested (primary) stop and the direction to the backup stop are clearly visible side by side.

### Changed
- **Unified In-Place Minimize Across All Layouts**: `RangeControlPanel`'s minimize/expand now behaves the same in the compact/vertical (mobile) layout as it already did in the wide/split layout — minimizing no longer slides the whole panel down; it just hides the sliders/climate-toggle block in place, leaving the car name + range summary always visible. Removed the now-unused swipe-to-minimize drag handle, `PanResponder`, and slide animation, since the panel itself never moves in either layout anymore.

### Fixed
- **Custom Start Point Reverted to GPS on Selection**: Picking a new "FROM" location in the trip planner called `mapRef.recenter()` to pan the map, but `recenter()` re-fetches the device's live GPS position and overwrites `userLocation` with it — silently snapping the just-picked custom start point back to the actual GPS location a moment later, so the trip was calculated from the old origin instead. Added a GPS-free `panTo(coords)` map method for this case; `recenter()` remains only for the explicit "Current Location" action.
- **Arrival Battery % Shown on Direct Routes**: `TripItinerary`'s "route safe, no charging needed" summary now shows the estimated arrival battery percentage (`plan.finalArrivalSoC`), matching the "Arrive with ~X% battery remaining" line already shown when charging stops are required. Previously this figure was computed by `TripPlannerService` but only surfaced in the UI when at least one charging stop was needed.

### Changed
- **In-Place Minimize for Wide/Split Layout**: `RangeControlPanel`'s minimize/expand toggle now behaves differently per layout. Compact (mobile) is unchanged — minimizing slides the whole panel down to peek from the bottom edge. In the wide/split layout, minimizing no longer shifts the panel's position at all; it just hides the sliders/climate-toggle block in place, leaving the car name and range summary (safe range, usable energy, max buffer, time budget) always visible in the right-hand column. The drag handle (a slide affordance) is hidden in wide mode since nothing slides there; tapping the summary card still toggles it.

### Fixed
- **Restored Live Location Search, Routing & Station Data**: Reverted the "100% offline" stubs added earlier today (`searchLocations`, `fetchRealRoute`, `fetchIsochronePolygon`, `getAllRealStations`) that unconditionally returned empty/null, which broke destination search (always "No matches found") and forced every trip route and range polygon onto the straight-line/simulated fallback instead of real road/OSM data. Real network calls (Nominatim, OSRM, OpenRouteService, OpenChargeMap/Overpass) are back, each still with its existing timeout + offline fallback if the request fails.

### Added
- **iOS Light/Dark App Icon**: Split the app icon into a light variant (`assets/icon-light.png`, generated by compositing the existing transparent glyph onto the app's light-theme background color) alongside the existing dark one (`assets/icon.png`), wired up via `ios.icon.light` / `ios.icon.dark` in `app.json`. On iOS 18+ (native build required — not visible in Expo Go), the Home Screen icon now switches automatically with the device's system Light/Dark Mode. Android has no equivalent OS-level icon-swap mechanism; it keeps its existing single adaptive icon with a monochrome layer for Android 13+ themed-icon tinting.
- **Dynamic System Theme Support**: The app now defaults to a `system` theme preference that follows the OS light/dark setting live (no restart needed), via a new `useResolvedThemeMode` hook subscribed to `useColorScheme`. The theme toggle button cycles system → light → dark → system, and `app.json`'s `userInterfaceStyle` was switched from a hardcoded `"dark"` to `"automatic"` so native chrome matches too.
- **Native Android Project & App Icon Asset Pack**: Added the native `android/` project scaffold (`expo prebuild`) and a generated brand icon set (`assets/icon.png`, adaptive-icon foreground/background, Android 13+ monochrome layer, splash, favicon, plus a reference `assets/app-icons/` export pack), wired up in `app.json`. Added `npm run android` / `npm run ios` scripts for native builds.
- **Dynamic Charging Speed Display**: Implemented active vehicle AC and DC peak charging limits inside the `RangeControlPanel` header.
- **Simulated Fallback Indicator**: Added a subtle, permanent `(Simulated)` badge next to the vehicle name pill and a footer note to notify users when range boundaries are rendered in offline simulation mode.
- **Scrollable Trip Itinerary**: Wrapped the timeline inside a `ScrollView` with a dynamic `maxHeight` restricted to 45% of the total screen height to prevent layout overflows.
- **Garage Preservation Policy**: Prevented default preset vehicle models (Tesla, BYD, NETA, MG, Hyundai) from being modified or deleted in the garage selector modal, securing system-default specifications.
- **Safety Fallback spec lookup**: Integrated a fallback mechanism that fetches vehicle specifications from presets if local persisted AsyncStorage profiles contain null or outdated values.

### Changed
- **Improved Fallback Polygon Formula**: Replaced the heavily distorted polygon formulas with a realistic road-network circuity (tortuosity) model scaling to 77%-87% of theoretical straight lines with organic variations.
- **Optimized Network Timeout Boundaries**: Wrapped all remote network fetches (OpenStreetMap Overpass, OpenChargeMap, OSRM routes, and OpenRouteService isochrones) with a hard 3-to-4-second timeout limit to guarantee instant offline fallback and prevent UI rendering hangs.
- **Cleaned Up Map Layout**: Removed the large floating warning overlay banners from the map layer for a cleaner, distraction-free user interface.
- **Responsive Split Layout for Wide Screens & Foldables**: `HomeScreen` now switches to a left/right split layout (search & trip card on the left, vehicle/range panel on the right) whenever the *shorter* screen dimension is at least 600dp, rather than requiring a landscape aspect ratio — this correctly triggers the split view on an unfolded Z Fold-style device (wide but still portrait-shaped), not just landscape tablets. `RangeControlPanel` gained an `isWide` prop so it renders fully expanded (no minimize handle) in that layout.
